# svelte-zukan design

"zukan" means "illustrated encyclopedia" in Japanese (図鑑).

## Goal

In an app that runs on Vite 8 and Svelte 5 (both plain Vite + Svelte and SvelteKit), placing `Foo.zukan.svelte` and `Foo.zukan.md` next to a component gives you a list, a per-section preview, and a code view. The only thing the consumer has to do is add `zukan()` to `vite.config.ts`. No routes and no config files are required in `src`. The dev server opens the catalog at `/__zukan/` (the same idea as vite-plugin-inspect's `/__inspect/`). When configured, `vite build` also writes the catalog out as a static SPA. In a monorepo, the catalog files of the workspace packages that the catalog app depends on are collected automatically.

### Background

1. The first design made consumers write `import.meta.glob` and put the catalog in a SvelteKit route (because a glob pattern cannot be received as a config value)
2. If the plugin enumerates the files itself and exposes the list as a virtual module, no glob is needed. One or two route files would still remain (SvelteKit 3.0.1 has no API for a plugin to add routes)
3. Following the request "I don't want to write anything in production code; configuration should stay inside vite.config", we dropped SvelteKit routes. The catalog is now an SPA that the plugin serves from the dev server

As a result, the earlier property "it runs inside a SvelteKit route, so Providers and layouts just work" is gone. Instead, the `wrapper` option specifies the Provider and global CSS. We do not build a standalone CLI (it ships as a Vite plugin).

## Findings from the spike

Verified with SvelteKit 3.0.1 and Vite 8.3.4, using a throwaway setup (not committed).

- Calling `server.middlewares.use` directly in `configureServer` lets us handle `/__zukan/` before SvelteKit's middleware. The HTML goes through `server.transformIndexHtml` and loads a virtual entry module (`/@id/__x00__virtual:...`). The app's own pages keep working as they are
- HMR: with both the app tab and the `/__zukan/` tab open, editing a component updates both without a reload
- Files outside Vite's root can be imported (via `/@fs/`). `#lib` is resolved by the `package.json` of the package that the loaded file belongs to (the app's `#lib/label.js` and package ui's `#lib/label.js` were resolved separately)
- In dev, the app and the catalog share a single module graph. `Hello.svelte` and `$app/state` were loaded from the same URL in both tabs. Swapping the resolution target depending on the importer would also affect the app itself, so it cannot be used
- `$app/state` loaded outside SvelteKit runs with the defaults of Kit's runtime code (`page.url` is `a:`, so `pathname` is an empty string, and `params` is `{}`). `browser` from `$app/env` is `true`. `goto` from `$app/navigation` only rejects and the screen does not navigate
- Build: adding `environments.zukan` (`consumer: 'client'`) in the `config` hook and calling `builder.build(builder.environments.zukan)` in the `buildApp` hook writes the catalog to a separate directory. It is not erased by the adapter's output. In the spike it ran before Kit's build, but the implementation sets `buildApp` to `order: 'post'`, so it runs after Kit's ssr and client builds and prerendering, and before the adapter
- The build inherits the `base: './'` that Kit puts into the shared config and its output file name rules, so using HTML as the input shifts the asset paths. Building only the JS entry and letting the plugin write the HTML worked under a subpath (e.g. `/zukan-dist/`) with relative paths
- The build environment needs the replacements that Kit defines only for its client environment. Without `__SVELTEKIT_PAYLOAD__`, components using `$app/*` threw a `ReferenceError` at render time. Inspecting the output also showed `__SVELTEKIT_HAS_SERVER_LOAD__` and `__SVELTEKIT_HAS_UNIVERSAL_LOAD__` left in the client runtime code that `$app/navigation` loads. With all three defined, no `__SVELTEKIT_*__` remained in the output, and `goto` in the built version only rejected without throwing
- Detecting Kit: it worked to await and flatten the consumer's `plugins` in the `config` hook and treat the app as Kit if any plugin name starts with `vite-plugin-sveltekit` (`sveltekit()` returns a Promise, so the await is needed). Rewriting the environment's `define` in `configResolved` did not take effect in the build
- Kit's plugin also outputs `_app/version.json` into the catalog's environment (harmless)

## Consumer setup

```ts
// vite.config.ts
import { zukan } from 'svelte-zukan/vite';
export default defineConfig({ plugins: [zukan(), sveltekit()] }); // zukan() goes before sveltekit()
```

- Start the dev server and open `/__zukan/`. The catalog URL is also added to the URL list printed in the terminal at startup
- To write it out statically, use `zukan({ build: true })`. `vite build` then writes the catalog to `zukan-dist/`, separately from the app build

## Options

```ts
zukan({
  suffix?: string; // default 'zukan'
  groups?: Record<string, string | string[]>; // group name → directories to search (relative to the Vite root)
  wrapper?: string; // path of the .svelte that wraps the preview (relative to the Vite root)
  logo?: string | false; // path of the logo image (relative to the Vite root). false hides it
  title?: string; // alt of the sidebar logo and <title>. default 'zukan'
  locale?: 'en' | 'ja'; // UI language. default 'en'
  build?: boolean | { outDir?: string }; // default false. when true, outDir is 'zukan-dist'
});
```

- There are exactly these 7 options. We added the logo, language, and static output requests to the requested "something like `suffix`, `groups`, and `wrapper`"
- All paths are relative to the Vite root, so they can point to a directory outside `src` such as `.zukan/`
- Invalid values (`suffix` not matching `/^[a-z0-9-]+$/i`, an unknown `locale`, a specified file or directory that does not exist) raise an error when the plugin is created or in `configResolved`

### Why `build` is off by default

If it were on by default, every `vite build` of the app would also build the catalog and create `zukan-dist/` without the user noticing. Only people who want to publish the catalog turn it on.

## File layout

```text
src/lib/Button/
├── Button.svelte
├── Button.zukan.svelte
└── Button.zukan.md      (optional)
```

- Catalog files sit directly next to the component (no subdirectory such as `zukan/`)
- `Foo.zukan.md` corresponds one-to-one to `Foo.zukan.svelte` (same directory, same `Foo`, same suffix)
- The suffix can be changed with `suffix` (with `zukan({ suffix: 'catalog' })`, the files are `*.catalog.svelte` / `*.catalog.md`). The suffix follows the configured value in all of these: id matching (the transform filter), file enumeration, watching, `hotUpdate`, the `.md` file name, and building the ID and display name. Escape it when putting it into a regular expression

## Writing catalog files

```svelte
<!-- src/lib/Button/Button.zukan.svelte -->
<script lang="ts">
  import { Section } from 'svelte-zukan';
  import Button from './Button.svelte';

  let count = $state(0);
  const label = $derived(`${count} clicks`);
</script>

<Section title="Basic">
  <Button onclick={() => count++}>{label}</Button>
</Section>

<Section title="Disabled">
  <Button disabled>Disabled</Button>
</Section>
```

- Put `<Section>` at the top level (not inside another element or block). `title` must be a non-empty static string. In the following cases the plugin fails the build (printing the file name and line). The message differs for each case
  - `title` is missing
  - `title` is a dynamic value (`title={x}`)
  - `title` is an empty string or only whitespace
  - `title` is duplicated within the same file
  - `<Section>` is somewhere other than the top level
- If `Foo.zukan.md` exists, it is shown as HTML at the top of the detail page

## Discovery (zero-config)

When `groups` is not given, the plugin searches in this order.

1. The `src` of the package at the Vite root (the catalog app itself)
2. For the app's `package.json` `dependencies` and then `devDependencies`, in that order, resolve the realpath of `<root>/node_modules/<name>`. Only those whose realpath does not contain `node_modules` (that is, workspace links) are considered, and the `src` of each such package is searched

- Only the `src` of each package is searched. Searching from the package root risks picking up catalog files copied into `dist`, for example
- Enumeration uses Node's `fs.globSync` (stable in Node 22.17 and later, which Kit 3 requires). No new dependency is added
- The group name is the `name` in that package's `package.json` (the directory name if there is none). The order is the app itself first, then the dependencies in declaration order. A package with no catalog files does not become a group
- A package whose `name` is `svelte-zukan` (a workspace link to this library itself) is not searched. This keeps the library's internal catalog files out of the consumer's catalog
- Transitive dependencies are not searched. Apps or packages that are not declared as dependencies (for example, reading another app `apps/web` from the catalog app) are specified with `groups`. The README gives an example
- When `groups` is given, automatic discovery is not performed and only the listed directories are searched. The order is the key order. A directory that does not exist is an error

## Catalog IDs

Catalog files with the same name must be handled even within the same package (group). For example, `src/lib/forms/Button.zukan.svelte` and `src/lib/nav/Button.zukan.svelte`. This can easily happen in a large package (100 or more catalogs in one package).

### How IDs are determined

- The ID is `<group>/<rel>`. `<rel>` is the relative path from the search directory (each package's `src` for automatic discovery, the listed directory for `groups`) to the catalog file, with `.<suffix>.svelte` removed
  - `src/lib/forms/Button.zukan.svelte` → `lib/forms/Button`
- When the last two segments are the same (`Button/Button`), they are merged into one. This keeps the URL from becoming redundant when a component is put in its own directory
  - `src/lib/Button/Button.zukan.svelte` → `lib/Button`
- `name` is the file name with `.<suffix>.svelte` removed (for display). `dir` is what remains of `<rel>` after removing `name` (an empty string at the root)
- The ID is used for URLs inside the catalog. It does not change unless the file is moved

### Alternatives considered

| Option                                                            | Advantages                                                                                                                 | Disadvantages                                                                                                                                                         |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use the path relative to the search directory as the ID (adopted) | Always unique and does not change when other files are added or removed. The directory structure shows up in the URL as is | URLs get long. Automatic discovery adds `lib/`                                                                                                                        |
| Add the directory only when names collide                         | URLs are short in the usual case                                                                                           | The moment a second file with the same name is added, the URL of the first one changes too                                                                            |
| Drop the prefix shared by all files in a group                    | Automatic discovery does not add `lib/` either                                                                             | Adding a single file outside the shared part changes the URLs of all files                                                                                            |
| Show the sidebar as a hierarchy                                   | Stays readable beyond 100 entries                                                                                          | The UI implementation gets large (open/closed state, expanding to the current location, keyboard navigation). It can be solved separately from how IDs are determined |

- We prioritize "URLs do not change when other files are added or removed" and use the relative path as is
- Automatic discovery adds `lib/` because it searches the whole `src`; we accept this. If it bothers you, specify `src/lib` with `groups`

### Possible collisions

Only the following two cases collide, and both are errors (print both file paths).

- When the merged result is the same: `lib/Button.zukan.svelte` and `lib/Button/Button.zukan.svelte`
- When the combination of group name and directory is the same: `ui/Card` in group `@acme` and `Card` in group `@acme/ui`

A group name that starts with `preview` or `preview/` is also an error (a reserved word in the URL below).

## URL

The catalog is an SPA that routes by hash.

| URL                                       | Shows                                  |
| ----------------------------------------- | -------------------------------------- |
| `/__zukan/`                               | List                                   |
| `/__zukan/#/<ID>`                         | Detail page                            |
| `/__zukan/#/preview/<ID>?section=<title>` | Preview for the iframe (no catalog UI) |

In the static output, the `/__zukan/` part becomes the output location (`zukan-dist/index.html`).

### Why hash routing

| Option                 | Advantages                                                                                                                                                       | Disadvantages                                                                                                                                                    |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hash (adopted)         | Only one HTML file is needed. Deep links open as they are wherever the output is placed (no server rewrite configuration needed). No need to compute a base path | The URL contains `#`                                                                                                                                             |
| Path (`/__zukan/<ID>`) | Clean URLs                                                                                                                                                       | The static output must write an HTML file per ID, or the hosting needs SPA rewrite configuration. A base path has to be computed depending on where it is placed |

- The earlier `resolveBase` and `page.params` are no longer needed
- Reserved word: a hash path that starts with `preview/` is a preview. An ID always starts with the group name, and the group names `preview` and `preview/...` are forbidden, so they do not collide. `preview` in the middle, as in `ui/preview/Foo`, has no effect
- Group names containing `/` (`@acme/ui`): `#/@acme/ui/lib/Card`. Lookup is by exact match on the ID, so the number of segments does not matter
- Links apply `encodeURIComponent` to each segment of the ID. When reading, apply `decodeURIComponent` to each segment
- `?section=` is read as a query inside the hash (split `location.hash` at `?`)

## Screens

### Sidebar

- The logo at the very top (a link to the list). The default is the bundled horizontal logo (an icon showing a dark gray book cover with a spine on the left edge and pages along the bottom edge, an orange Svelte S, and an orange bookmark hanging from the top right, plus the text "zukan". The text is drawn as paths and does not depend on fonts). `src/lib/app/logo.svg` (light version, viewBox `0 0 412 128`) is displayed at about 32px high. The dark version (`.github/logo-dark.svg`) has the same shape, distinguished from a black background by the cover's edge and a lighter spine. It is used only in the README
  - Specifying an image path such as `logo: './.zukan/logo.svg'` replaces it. The plugin loads it in the virtual entry as `import logo from '<abs>?url'`, so the same notation works in both dev and build
  - With `logo: false`, no logo is shown and the `title` string is displayed instead
  - The logo's `alt` is `title` (default `zukan`)
  - The link target is fixed to the list (we will add this if someone asks for an external link)
  - `logo` accepts only the light one. The catalog UI is light only and has no dark mode (the theme's only default is light, and consumers have no way to override it), so there would be no use for a dark logo. When dark mode is added, `logo` will be widened to also accept the `{ light, dark }` form
- Below it, the list. It follows the order of the virtual module (group order; within a group, `<rel>` order, so directories stay together). `<rel>` is compared with `new Intl.Collator('en', { numeric: true, sensitivity: 'base' })` (case-insensitive, with `Item2` before `Item10`), and ties are broken by code point order. Sorting is done once on the plugin side (Node), so the order does not vary between browsers. Each item mainly shows `name`, and if there is a `dir`, it is added in a muted color (for example, `Button` `lib/forms`). Files with the same name are told apart by this `dir`. Each item gets a badge with the group name

### Favicon

- The generated HTML's `<link rel="icon" type="image/svg+xml">` embeds the bundled standalone icon (`src/lib/app/icon.svg`, light version, viewBox `0 0 120 128`) as a data URL. It works the same in dev and build, without serving a file or copying an asset
- Replacing `logo` does not change the favicon (to avoid adding options; we will add it if requested)

### `<title>`

- On the list: `title` (default `zukan`)
- On a detail page: `<name> | <title>`

### List and detail

- List page: the same list as the sidebar is also shown in the body. If there are no catalog files at all, it says so and shows where it searched (groups and directories)
- Detail page: `name`, `dir`, badge, the `.md` HTML, and for each section a vertical stack of "heading, preview, code"
- A nonexistent ID shows a "not found" message
- A catalog file that failed to load shows the error contents

### Preview

- One `<iframe src="./#/preview/<ID>?section=<title>">` per section (the same HTML as the catalog)
- The preview side does not show the catalog UI. If `wrapper` is given, it wraps with it and renders the whole catalog file. `Section` compares the context's `section` with its own `title` and renders `children` only on a match. Where there is no context (rendering directly outside the catalog, or a preview without a `section`), it always renders
- `wrapper` is dynamically imported only for the preview. Even if `wrapper` imports global CSS, it is not loaded into the catalog's UI side
- The height fits the content. Since it is same-origin, the parent observes the wrapper element inside `iframe.contentDocument` with a `ResizeObserver`
- The width is kept per section. It is changed with preset buttons (375 / 768 / 1024 / 1280px and "100%") and by dragging a handle at the right edge of the frame. The current width is shown in px. During a drag, `pointer-events: none` is set on the iframe. The default is 100%
- The handle follows the WAI-ARIA window splitter pattern: `role="separator"`, `aria-valuenow` / `aria-valuemin` / `aria-valuemax`, the left and right keys move by 10px, Home goes to the minimum width, End to the maximum width. When the viewport is narrower than the minimum width (200px), `aria-valuemin` is set to the viewport width so that `aria-valuenow` never falls below `aria-valuemin`
- Until the viewport width has been measured, the width display and the handle's aria values are not shown (so 0px is never flashed)

### `wrapper`

```svelte
<!-- .zukan/Wrapper.svelte -->
<script lang="ts">
  import '../src/app.css';
  import ThemeProvider from '../src/lib/ThemeProvider.svelte';
  let { children } = $props();
</script>

<ThemeProvider>{@render children()}</ThemeProvider>
```

- The counterpart of Storybook's `.storybook/preview.js`. It receives `children` and renders them
- It can be placed outside `src` (for example, `.zukan/`)

### Code view

- Extract the contents of the section (between the opening and closing tags of `<Section>`) and align the indentation
- Of the identifiers referenced in the template, attach the definitions of those defined at the top level of the instance script (`import`, `let`/`const`/`var`, `function`, `class`) as a `<script>` block at the top. Definitions that those definitions reference are included as well. The original order is preserved. Imports from `svelte-zukan` are excluded
- Inherit the `lang` of the original file's `<script lang="ts">`
- Collapse it with `<details>`, closed by default. The copy button goes in a toolbar on the same line as the `<summary>` and does not overlap the code (the earlier approach of reserving fixed space on the right of the `pre` is dropped)
- Copying uses `navigator.clipboard.writeText`. If it fails (no permission, opened over HTTP, and so on), a message saying so is shown for 2 seconds
- No syntax highlighting

## Supported environments

- A library for Svelte (Vite), with SvelteKit treated as one of the supported targets. Neither the plugin nor the catalog SPA depends on SvelteKit. The same `zukan()` works with plain Vite + Svelte (`@sveltejs/vite-plugin-svelte`'s `svelte()`) and with SvelteKit
- Align the README text, the `package.json` `description` (for example, `Colocated component catalog for Svelte, served by a Vite plugin`), and `keywords` (`svelte`, `vite-plugin`, `component-catalog`, `styleguide`; keep `sveltekit` as a supported target) with this positioning
- Requirements are Vite 8 or later (the `buildApp` hook and the Environment API), Svelte 5, and Node 22.17 or later
- The Kit-specific handling (the define below) is added only when Kit is detected. Detection awaits and flattens the consumer's `plugins` in the `config` hook and checks whether any plugin name starts with `vite-plugin-sveltekit` (confirmed in the spike). It is not decided by whether `@sveltejs/kit` is installed (in a monorepo it can be visible even from apps that do not use Kit)
- Verify both plain Vite + Svelte and SvelteKit with fixtures (Task 7 of the plan). For plain Vite, verify `/__zukan/` in dev, HMR, `build: true`, and rendering of components that do not use `$app/*`

## SvelteKit runtime APIs

- No swapping. As the spike showed, in dev the app and the catalog share a single module graph, so the resolution target cannot be changed for the catalog only. Swapping only in the build would make dev and build behave differently, so we swap in neither
- Inside the catalog, Kit's runtime code runs in its default state
  - `page` from `$app/state`: `url.pathname` is an empty string, `params` is `{}`, `data` is `{}`
  - `browser` from `$app/env`: `true`
  - `goto` and the like from `$app/navigation`: they only reject and the screen does not navigate
- Displays that depend on this (such as navigation that changes with the current page) appear with the default values in the catalog. Document this in the README
- Only when Kit is detected, put `define: { __SVELTEKIT_PAYLOAD__: 'undefined', __SVELTEKIT_HAS_SERVER_LOAD__: 'false', __SVELTEKIT_HAS_UNIVERSAL_LOAD__: 'false' }` into the build environment
- This define relies on SvelteKit's internal implementation (replacements defined only for the client environment). To notice when a Kit update adds other replacements or renames them, add an automated test that builds the SvelteKit fixture and checks that no identifier starting with `__SVELTEKIT_` and ending with `__` remains in the catalog's output. Renovate auto-merges Kit minor updates, so make it run in CI (Task 7 of the plan)
- How `resolve` / `asset` from `$app/paths` behave inside the catalog is verified in the plan's verification steps and documented in the README

## Watching

- Search directories outside the Vite root are added with `server.watcher.add` in `configureServer`
- `hotUpdate` handles the following
  - Creation and deletion of `*.<suffix>.svelte` inside a search directory: invalidate the list's virtual module in each environment
  - Changes to `*.<suffix>.svelte`, and creation, change, and deletion of `*.<suffix>.md`: invalidate the module of the corresponding `.svelte`
  - In the client environment, send the custom event `zukan:reload` instead of `full-reload`. The catalog SPA receives it with `import.meta.hot.on('zukan:reload')` and reloads only itself. `full-reload` would also reload the app's tabs connected to the same dev server
- The reason for not doing partial HMR is unchanged (`__zukan` is an export outside the component, so Svelte's HMR does not swap it). Changes to the component itself go through normal HMR and are reflected in both the app and the catalog

## `server.fs.allow`

- Only when a search directory, or the library's own directory (the `dist/` that contains `appFile`; `src/lib/` in this repository), is outside the Vite root, add it to `server.fs.allow` in the `config` hook. Only those outside the root are added
- Compare against the root, not `searchForWorkspaceRoot(root)`. SvelteKit (confirmed with 3.0.1) always sets `server.fs.allow` to an explicit list, so Vite's default of allowing the workspace root does not take effect
- The library's own directory is also covered. Files fetched by URL, such as the catalog SPA and the logo (`?url`), are rejected by `fs.allow` if they are outside the root. When installed via the pnpm store or a link, the library's real location is outside the root
- When adding, also include `searchForWorkspaceRoot(root)` (an explicit `allow` stops the default from being used). If the consumer has written `allow`, append to that value (the result is `[searchForWorkspaceRoot(root), ...allow, ...directories outside the root]`)

## Vite plugin `zukan()`

Build it following [Vite's Plugin API](https://vite.dev/guide/api-plugin).

- Name: `name: 'vite-plugin-svelte-zukan'`
- `enforce: 'pre'`. It transforms before vite-plugin-svelte compiles. The README tells consumers to put `zukan()` before `sveltekit()`
- dev: call `server.middlewares.use` directly in `configureServer` and return HTML for requests that start with `/__zukan/`. The HTML goes through `server.transformIndexHtml` and loads the virtual entry `\0virtual:svelte-zukan/entry`. The plan verifies that it also works in an app with Vite's `base` set
- What the virtual entry imports
  - The library's SPA itself (an absolute path computed relative to the plugin file's location: `dist/app/App.svelte` in dist, `src/lib/app/App.svelte` in this repository). Since no bare specifier is used, this repository needs no self-referencing alias
  - The list's virtual module `\0virtual:svelte-zukan/catalog`
  - The logo (`?url`), the `wrapper` path, `locale`, and `title`
- The list's virtual module:

```ts
export const catalog = [
  { group: 'ui', name: 'Button', dir: 'forms', path: 'ui/forms/Button', load: () => import('/abs/path/to/forms/Button.zukan.svelte') },
  ...
];
```

- The import target of `load` is a `normalizePath`-ed absolute path
- Build (when `build` is enabled)
  - In the `config` hook (`order: 'post'`), add `environments.zukan` (`consumer: 'client'`, the define above only when Kit is detected, the input is the virtual entry's JS, output file names follow a fixed rule such as `_zukan/[name]-[hash].js`, `copyPublicDir: false`). Also add `builder: {}`. Without `builder`, a plain `vite build` creates only the client environment. For `vite build --ssr` (the server side of an SSR build), nothing is added
  - The environment's `build` inherits the app's top-level `build`. The `configEnvironment` hook makes the input only the virtual entry and removes `ssr` and `lib`
  - Make it placeable under a subpath: `base` cannot vary per environment, so in plain Vite with `base: '/'` left as is, the catalog JS preloads become absolute paths. Wrap `experimental.renderBuiltUrl` and return `{ relative: true }` for files under `_zukan/`. Other files are left to the existing function (Kit's or the consumer's)
  - `buildApp` hook (`order: 'post'`): if no other hook has built any environment, build the app first. This is because Vite builds the app only when no hook has built an environment. Then call `builder.build(builder.environments.zukan)`, find the chunk named `zukan` in the output, and write `<outDir>/index.html` with relative paths (`./_zukan/...`). With `--watch`, print a warning and skip the catalog
  - Delete the `_app/version.json` that Kit emits. Delete `_app` only if it becomes empty
  - It works the same way in apps that do not use SvelteKit (`buildApp` is a hook of Vite itself)
  - Clear the previous output: in the catalog's environment, always set `emptyOutDir` to `false`, and before writing, delete only what the plugin writes (`<outDir>/_zukan/` and `<outDir>/index.html`)
    - Reason: Kit sets `emptyOutDir: false` for the whole build and the catalog's environment inherits it, so the previous `_zukan/*` kept remaining. On the other hand, emptying the whole output with Vite's `emptyOutDir` would also delete unrelated files when the consumer shares the output directory with something else (for example, inside `docs/`)
    - Since only what the plugin writes is deleted, it is safe even when the output is outside the Vite root. The deletion targets are limited to the two entries directly under the output directory
  - Output directory overlap check (when `build` is enabled and it is not `vite build --ssr`)

    | Overlaps with                                              | Handling | Reason                                                                                                                                                                                                                                                                                                                                             |
    | ---------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
    | The Vite root itself                                       | Error    | It would write and delete `index.html` and `_zukan/` in the root                                                                                                                                                                                                                                                                                   |
    | The app's `build.outDir`                                   | Error    | The app's output and the catalog's output would overwrite each other. The value can be read reliably from the plugin                                                                                                                                                                                                                               |
    | SvelteKit's `kit.outDir` (default `.svelte-kit`)           | Error    | A directory managed by Kit and recreated on every build. The value can be read reliably from `api.options` of Kit's plugin                                                                                                                                                                                                                         |
    | `<root>/build`, a common SvelteKit adapter output location | Warning  | The default output of adapter-static and adapter-node; the adapter runs after the catalog and often wipes its contents. To avoid stopping the build on a guess, it stays a warning |
    - "Overlap" means that two directories are the same, or one is inside the other. Paths are compared after `normalizePath`
    - The `<root>/build` warning is shown only when Kit is detected. In plain Vite, no adapter uses `build/`
    - Warning and error messages are in English and show the catalog's output directory and the path it overlaps with. The warning adds guidance to specify another location with `build: { outDir }`
- `transform` uses a hook filter. The regular expression is built per `zukan()` call from the escaped suffix. Ids with `?` are also covered, but the virtual modules that vite-plugin-svelte creates for CSS (`?svelte&type=style&lang.css`) and virtual modules with `\0` are excluded. The same check is also done inside the handler (for older Vite / Rollup that do not support filters)
- Parsing uses `parse(source, { modern: true })` from `svelte/compiler`, and adds `export const __zukan = { sections, doc }`
  - If there is a `<script module>`, add it on one line at the start of its contents, without inserting a newline
  - If there is none, append a `<script module>` block to the end of the file
  - Insertion is done with `magic-string`, and a map is returned
- `.md` is converted to HTML with `marked` and registered as a dependency with `this.addWatchFile`
- The transform is called per environment. The result is determined only by the source and the `.md`, and does not branch on the environment
- Split the parsing, the discovery and list building, and the hash reading/writing into functions that can be unit tested
- It uses Vite-only hooks (`configureServer`, `hotUpdate`, `buildApp`), so it is not made a Rolldown-only plugin

## Appearance

- All scoped CSS. It does not depend on the consumer's Tailwind or the like. The catalog UI does not load the app's global CSS (`wrapper` applies only inside the preview iframe)
- The earlier public custom properties (9 of them, such as `--zukan-color-bg`) can no longer be overridden by consumers. The catalog UI is standalone HTML and loads neither the app's CSS nor `wrapper`. The default values remain as internal variables and are not treated as a public mechanism (the README table is also deleted). If someone asks to change the theme, we will add it as an option

## Out of scope

- Decorators, a standalone CLI, syntax highlighting, search, and a dark-mode default
- Swapping or mocking the SvelteKit runtime APIs (`$app/*`)
- A hierarchical (tree) sidebar. Showing `dir` is enough to tell same names apart, and the sort order keeps directories together. If the list turns out to be hard to scan beyond 100 entries, the display alone can be added without changing IDs
- Aliases such as `import { Section as S }`
- Attaching the definition when a top-level `{#snippet}` is referenced from a section
- Changing the catalog UI's theme through options (default values only for now)
- Changing the logo's link target, and a third or later UI language
- Discovery of transitive workspace dependencies
- Guaranteeing the order when `groups` keys are digits only. JavaScript objects place keys that look like integers (`'1'`, `'2'`) first in numeric order rather than declaration order. Using only digits as group names is rare, and not worth adding an array-shaped option. Write one line in the README
- A layout for narrow screens in the catalog UI. The catalog is used by developers in desktop browsers, and smartphone widths can be checked with the preview width presets
- Following the height when only the preview iframe is reloaded. Changes to catalog files or `.md` reload the whole catalog (`zukan:reload`), and component changes are handled by HMR inside the iframe, so there is no case where only the iframe is reloaded

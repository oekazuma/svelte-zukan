# svelte-zukan 設計

zukan は日本語で「図鑑」（illustrated encyclopedia）の意味。

## 目的

Vite 8 と Svelte 5 で動くアプリ（素の Vite + Svelte と SvelteKit の両方）のコンポーネントの隣に `Foo.zukan.svelte` と `Foo.zukan.md` を置くと、一覧・セクションごとのプレビュー・コード表示がそろう。利用側の作業は `vite.config.ts` に `zukan()` を足すことだけにする。`src` にはルートも設定ファイルも置かせない。dev サーバーでは `/__zukan/` でカタログを開ける（vite-plugin-inspect の `/__inspect/` と同じ考え方）。設定すれば `vite build` のときにカタログも静的な SPA として書き出す。モノレポでは、カタログ用のアプリが依存しているワークスペースパッケージのカタログファイルも自動で集める。

### 経緯

1. 最初は、利用側に `import.meta.glob` を書かせ、SvelteKit のルートにカタログを置く設計だった（glob のパターンは設定値として受け取れないため）
2. プラグインが自分でファイルを列挙し、仮想モジュールで一覧を出せば glob は要らない。それでもルートファイルは 1〜2 個残る（SvelteKit 3.0.1 にはプラグインからルートを足す API がない）
3. 「プロダクションのコードに何も書かせたくない。設定は vite.config の中で完結させたい」という要望を受けて、SvelteKit のルートを使うのをやめた。カタログはプラグインが dev サーバーに出す SPA にする

この結果、「SvelteKit のルートの中で動くので Provider やレイアウトがそのまま効く」という以前の特徴はなくなる。代わりに `wrapper` オプションで Provider とグローバル CSS を指定する。単体の CLI は作らない（Vite プラグインとして出す）。

## スパイクで確かめたこと

SvelteKit 3.0.1 と Vite 8.3.4 で、捨てる前提の構成（コミットしない）を使って確かめた。

- `configureServer` で `server.middlewares.use` を直接呼ぶと、SvelteKit のミドルウェアより前に `/__zukan/` を処理できる。HTML は `server.transformIndexHtml` を通し、仮想エントリモジュール（`/@id/__x00__virtual:...`）を読み込ませる。アプリ本体のページはそのまま動く
- HMR: アプリのタブと `/__zukan/` のタブを両方開いた状態でコンポーネントを編集すると、両方に再読み込みなしで反映される
- Vite の root 外のファイル（`/@fs/` 経由）を import できる。`#lib` は、読み込まれたファイルが属するパッケージの `package.json` で解決される（アプリの `#lib/label.js` とパッケージ ui の `#lib/label.js` が別々に解決された）
- dev ではアプリとカタログが 1 つのモジュールグラフを共有する。`Hello.svelte` と `$app/state` は、どちらのタブでも同じ URL で読まれた。読み込み元によって解決先を変える差し替えは、アプリ本体にも効いてしまうので使えない
- SvelteKit の外で読まれた `$app/state` は、Kit の実行時コードの既定値で動く（`page.url` は `a:` なので `pathname` は空文字、`params` は `{}`）。`$app/env` の `browser` は `true`。`$app/navigation` の `goto` は reject するだけで、画面は移動しない
- ビルド: `config` フックで `environments.zukan`（`consumer: 'client'`）を足し、`buildApp` フックで `builder.build(builder.environments.zukan)` を呼ぶと、Kit のビルドより先にカタログが別ディレクトリへ書き出される。adapter の書き出しには消されない
- ビルドでは、Kit が共有設定に入れる `base: './'` と出力ファイル名の規則を引き継ぐため、HTML を入力にすると asset のパスがずれる。JS のエントリだけをビルドし、HTML はプラグインが書き出す形にすると、相対パスでサブパス配下（例: `/zukan-dist/`）でも動いた
- ビルドの環境には、Kit が client 環境にだけ定義している置き換えが要る。`__SVELTEKIT_PAYLOAD__` がないと `$app/*` を使うコンポーネントが描画時に `ReferenceError` になった。さらに、出力を調べると `$app/navigation` が読み込むクライアント実行時コードに `__SVELTEKIT_HAS_SERVER_LOAD__` と `__SVELTEKIT_HAS_UNIVERSAL_LOAD__` が残っていた。3 つとも定義すると出力に `__SVELTEKIT_*__` は残らず、ビルド版でも `goto` は reject するだけで例外を出さなかった
- Kit の検出: `config` フックで利用側の `plugins` を await して平らにし、名前が `vite-plugin-sveltekit` で始まるプラグインがあれば Kit とみなす方法で検出できた（`sveltekit()` は Promise を返すので await が要る）。`configResolved` で環境の `define` を書き換える方法は、ビルドに反映されなかった
- Kit のプラグインは、カタログの環境にも `_app/version.json` を出力する（害はない）

## 利用側のセットアップ

```ts
// vite.config.ts
import { zukan } from 'svelte-zukan/vite';
export default defineConfig({ plugins: [zukan(), sveltekit()] }); // zukan() は sveltekit() より前
```

- dev サーバーを起動し、`/__zukan/` を開く。起動時のターミナルの URL 一覧にもカタログの URL を足す
- 静的に書き出すときは `zukan({ build: true })`。`vite build` で、アプリのビルドとは別に `zukan-dist/` へカタログが出る

## 設定

```ts
zukan({
  suffix?: string; // 既定 'zukan'
  groups?: Record<string, string | string[]>; // グループ名 → 探すディレクトリ（Vite の root からの相対）
  wrapper?: string; // プレビューを囲む .svelte のパス（Vite の root からの相対）
  logo?: string | false; // ロゴ画像のパス（Vite の root からの相対）。false で非表示
  title?: string; // サイドバーのロゴの alt と <title>。既定 'zukan'
  locale?: 'en' | 'ja'; // UI の言語。既定 'en'
  build?: boolean | { outDir?: string }; // 既定 false。true なら outDir は 'zukan-dist'
});
```

- 項目はこの 7 つにする。依頼の「`suffix`、`groups`、`wrapper` 程度」に、ロゴ、言語、静的書き出しの要望の分を足した
- パスはすべて Vite の root からの相対で、`.zukan/` のような `src` 外のディレクトリに置ける
- 不正な値（`suffix` が `/^[a-z0-9-]+$/i` に合わない、`locale` が未知、指定したファイルやディレクトリがない）は、プラグインの生成時か `configResolved` でエラーにする

### `build` を既定で off にする理由

既定で on にすると、アプリを `vite build` するたびにカタログのビルドが走り、知らないうちに `zukan-dist/` ができる。カタログを公開したい人だけが on にする。

## ファイル配置

```text
src/lib/Button/
├── Button.svelte
├── Button.zukan.svelte
└── Button.zukan.md      （任意）
```

- カタログファイルはコンポーネントの隣に直接置く（`zukan/` のようなサブディレクトリは使わない）
- `Foo.zukan.md` は `Foo.zukan.svelte` と 1 対 1 で対応する（同じディレクトリ、同じ `Foo`、同じ接尾辞）
- 接尾辞は `suffix` で変えられる（`zukan({ suffix: 'catalog' })` なら `*.catalog.svelte` / `*.catalog.md`）。接尾辞は、id 判定（transform のフィルター）、ファイルの列挙、監視、`hotUpdate`、`.md` のファイル名、ID と表示名の作成のすべてで設定値に従う。正規表現に入れるときはエスケープする

## カタログファイルの書き方

```svelte
<!-- src/lib/Button/Button.zukan.svelte -->
<script lang="ts">
  import { Section } from 'svelte-zukan';
  import Button from './Button.svelte';

  let count = $state(0);
  const label = $derived(`${count} clicks`);
</script>

<Section title="Basic">
  <Button onclick={() => count++}>{label}</Button>
</Section>

<Section title="Disabled">
  <Button disabled>Disabled</Button>
</Section>
```

- `<Section>` はトップレベル（他の要素やブロックの中ではない位置）に置く。`title` は空でない静的な文字列のみ。次の場合はプラグインがビルドエラーにする（ファイル名と行を出す）。メッセージは場合ごとに分ける
  - `title` がない
  - `title` が動的な値（`title={x}`）
  - `title` が空文字や空白だけ
  - 同じファイル内で `title` が重複
  - `<Section>` がトップレベル以外にある
- `Foo.zukan.md` があれば、詳細ページの上部に HTML として表示する

## 探索（ゼロコンフィグ）

`groups` がないとき、プラグインが次の順に探索する。

1. Vite の root にあるパッケージ（カタログ用のアプリ自身）の `src`
2. そのアプリの `package.json` の `dependencies` → `devDependencies` の順に、`<root>/node_modules/<name>` の realpath を求める。realpath に `node_modules` が含まれないもの（= ワークスペースのリンク）だけを対象にし、そのパッケージの `src` を探す

- 探すのは各パッケージの `src` だけにする。パッケージ直下から探すと、`dist` にコピーされたカタログファイルなどを拾う危険があるため
- 列挙は Node の `fs.globSync`（Kit 3 の要件である Node 22.17 以上で stable）。新しい依存は足さない
- グループ名はそのパッケージの `package.json` の `name`（なければディレクトリ名）。並び順はアプリ自身のあと、依存の宣言順。カタログファイルがないパッケージはグループにしない
- 推移的な依存は探さない。依存に宣言していないアプリやパッケージ（例: カタログ用のアプリから別のアプリ `apps/web` を読む）は `groups` で指定する。README に例を書く
- `groups` を書くと自動探索は行わず、書いたディレクトリだけを探す。並び順はキー順。存在しないディレクトリはエラー

## カタログの ID

同じパッケージ（グループ）の中に同名のカタログファイルがあっても扱えるようにする。たとえば `src/lib/forms/Button.zukan.svelte` と `src/lib/nav/Button.zukan.svelte`。大きなパッケージ（1 パッケージに 100 以上のカタログ）では十分に起こりうる。

### 決め方

- ID は `<group>/<rel>`。`<rel>` は、探索ディレクトリ（自動探索なら各パッケージの `src`、`groups` なら書かれたディレクトリ）からカタログファイルまでの相対パスから、`.<suffix>.svelte` を除いたもの
  - `src/lib/forms/Button.zukan.svelte` → `lib/forms/Button`
- 最後の 2 セグメントが同じとき（`Button/Button`）は 1 つにまとめる。コンポーネントをディレクトリに入れる書き方で URL が冗長にならないようにするため
  - `src/lib/Button/Button.zukan.svelte` → `lib/Button`
- `name` はファイル名から `.<suffix>.svelte` を除いたもの（表示用）。`dir` は `<rel>` から `name` を除いた残り（ルート直下なら空文字）
- ID はカタログ内の URL に使う。ファイルを動かさない限り変わらない

### 比べた案

| 案                                                 | 利点                                                                                | 欠点                                                                                                 |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 探索ディレクトリからの相対パスを ID にする（採用） | 必ず一意で、ほかのファイルの増減で変わらない。ディレクトリ構成がそのまま URL に出る | URL が長くなる。自動探索では `lib/` が付く                                                           |
| 同名のときだけディレクトリを添える                 | 普段の URL が短い                                                                   | 2 つ目の同名ファイルを足した瞬間に、1 つ目の URL まで変わる                                          |
| グループ内の全ファイルに共通する接頭辞を省く       | 自動探索でも `lib/` が付かない                                                      | 共通部分の外にファイルを 1 つ足すと、全ファイルの URL が変わる                                       |
| サイドバーを階層表示にする                         | 100 件を超えても見通せる                                                            | UI の実装が大きくなる（開閉の状態、現在地までの展開、キーボード操作）。ID の決め方とは別に解決できる |

- 「ほかのファイルの増減で URL が変わらない」ことを優先し、相対パスをそのまま使う
- 自動探索で `lib/` が付くのは `src` 全体を探すためで、受け入れる。気になれば `groups` で `src/lib` を指定する

### 起こりうる重複

重複するのは次の 2 つだけで、どちらもエラーにする（両方のファイルパスを出す）。

- まとめた結果が同じになるとき: `lib/Button.zukan.svelte` と `lib/Button/Button.zukan.svelte`
- グループ名とディレクトリの組み合わせが同じになるとき: グループ `@acme` の `ui/Card` と、グループ `@acme/ui` の `Card`

グループ名が `preview` か `preview/` で始まるときもエラー（下の URL の予約語）。

## URL

カタログはハッシュでルーティングする SPA にする。

| URL                                       | 表示                                      |
| ----------------------------------------- | ----------------------------------------- |
| `/__zukan/`                               | 一覧                                      |
| `/__zukan/#/<ID>`                         | 詳細ページ                                |
| `/__zukan/#/preview/<ID>?section=<title>` | iframe 用プレビュー（カタログの UI なし） |

静的書き出しでは `/__zukan/` の部分が書き出し先（`zukan-dist/index.html`）になる。

### ハッシュにする理由

| 案                      | 利点                                                                                                                                                 | 欠点                                                                                                                        |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| ハッシュ（採用）        | HTML が 1 つで済む。書き出したものをどのパスに置いても、深いリンクがそのまま開ける（サーバーの書き換え設定が要らない）。ベースパスを計算しなくてよい | URL に `#` が入る                                                                                                           |
| パス（`/__zukan/<ID>`） | URL がきれい                                                                                                                                         | 静的書き出しで ID ごとに HTML を書くか、ホスティング側に SPA 用の書き換え設定が要る。置き場所に応じたベースパスの計算が要る |

- 以前の `resolveBase` と `page.params` は不要になる
- 予約語: ハッシュのパスが `preview/` で始まるとプレビュー。ID は必ずグループ名で始まり、グループ名 `preview` と `preview/...` は禁止なので衝突しない。`ui/preview/Foo` のように途中にあっても影響しない
- `/` を含むグループ名（`@acme/ui`）: `#/@acme/ui/lib/Card`。ID の完全一致で探すので、セグメントの数は問わない
- リンクは ID の各セグメントを `encodeURIComponent` する。読むときは各セグメントを `decodeURIComponent` する
- `?section=` はハッシュの中のクエリとして読む（`location.hash` を `?` で分ける）

## 画面

### サイドバー

- 最上部にロゴ（一覧へのリンク）。既定はライブラリ同梱の横組みロゴ（濃灰の本の表紙に、左端の背表紙と下端のページ、オレンジの Svelte の S、右上から下がるオレンジのしおりを描いたアイコンと「zukan」の文字。文字はパスで描いてありフォントに依存しない）。`src/lib/app/logo.svg`（ライト版、viewBox `0 0 412 128`）を高さ 32px 程度で表示する。ダーク版（`.github/logo-dark.svg`）は同じ形で、表紙の縁と明るめの背表紙で黒い背景と分けたもの。README だけで使う
  - `logo: './.zukan/logo.svg'` のように画像のパスを指定すると差し替わる。プラグインが仮想エントリで `import logo from '<abs>?url'` として読むので、dev でもビルドでも同じ書き方で動く
  - `logo: false` ならロゴを出さず、`title` の文字列を表示する
  - ロゴの `alt` は `title`（既定 `zukan`）
  - リンク先は一覧に固定する（外部リンクにする要望が出たら足す）
  - `logo` はライト用の 1 つだけを受け取る。カタログの UI はライトだけでダークモードを持たない（テーマの既定値はライトのみで、利用側が上書きする手段もない）ため、ダーク用を受け取っても使う場面がない。ダークモードを入れるときに、`logo` を `{ light, dark }` の形でも受け取れるように広げる
- その下に一覧。仮想モジュールの並び順どおり（グループ順、グループ内は `<rel>` 順なのでディレクトリごとにまとまる）。`<rel>` の比較は `new Intl.Collator('en', { numeric: true, sensitivity: 'base' })`（大文字小文字を区別せず、`Item2` を `Item10` より前にする）で行い、同順位はコードポイント順で決める。並べ替えはプラグイン側（Node）で一度だけ行うので、ブラウザの違いで順序は変わらない。各項目は `name` を主に表示し、`dir` があれば控えめな色で添える（例: `Button` `lib/forms`）。同名のファイルはこの `dir` で見分ける。各項目にグループ名のバッジを付ける

### ファビコン

- 生成する HTML の `<link rel="icon" type="image/svg+xml">` に、同梱のアイコン単体（`src/lib/app/icon.svg`、ライト版、viewBox `0 0 120 128`）を data URL で埋め込む。dev でもビルドでも、ファイルの配信や asset のコピーなしで同じに動く
- `logo` を差し替えてもファビコンは変えない（オプションを増やさないため。要望が出たら足す）

### `<title>`

- 一覧では `title`（既定 `zukan`）
- 詳細では `<name> | <title>`

### 一覧と詳細

- 一覧ページ: サイドバーと同じリストを本文にも出す。カタログファイルが 1 つもなければ、その旨と探した場所（グループとディレクトリ）を表示する
- 詳細ページ: `name`、`dir`、バッジ、`.md` の HTML、セクションごとに「見出し、プレビュー、コード」を縦に並べる
- 存在しない ID は「見つからない」旨を表示する
- 読み込みに失敗したカタログファイルは、エラーの内容を表示する

### プレビュー

- セクションごとに `<iframe src="./#/preview/<ID>?section=<title>">`（カタログと同じ HTML）
- プレビュー側はカタログの UI を出さず、`wrapper` があればそれで囲んでカタログファイル全体を描画する。`Section` はコンテキストの `section` と自分の `title` を比べて、一致したものだけ `children` を描画する。コンテキストがない場所（カタログ外で直接描画した場合や、`section` 指定のないプレビュー）では常に描画する
- `wrapper` はプレビューのときだけ動的 import する。`wrapper` がグローバル CSS を import していても、カタログの UI 側には読み込まれない
- 高さは中身に合わせる。同一オリジンなので親が `iframe.contentDocument` 内のラッパー要素を `ResizeObserver` で監視する
- 幅はセクションごとに持つ。プリセットボタン（375 / 768 / 1024 / 1280px と「100%」）と、フレーム右端のハンドルのドラッグで変える。現在の幅を px で表示する。ドラッグ中は iframe に `pointer-events: none` を付ける。既定は 100%
- ハンドルは WAI-ARIA の window splitter に沿う。`role="separator"`、`aria-valuenow` / `aria-valuemin` / `aria-valuemax`、左右キーで 10px、Home で最小幅、End で最大幅。表示領域が最小幅（200px）より狭いときは `aria-valuemin` を表示領域の幅にそろえ、`aria-valuenow` が `aria-valuemin` を下回らないようにする
- 表示領域の幅を測るまでは、幅の表示とハンドルの aria 値を出さない（0px を一瞬出さない）

### `wrapper`

```svelte
<!-- .zukan/Wrapper.svelte -->
<script lang="ts">
  import '../src/app.css';
  import ThemeProvider from '../src/lib/ThemeProvider.svelte';
  let { children } = $props();
</script>

<ThemeProvider>{@render children()}</ThemeProvider>
```

- Storybook の `.storybook/preview.js` に当たる。`children` を受け取り、描画する
- `src` の外（例: `.zukan/`）に置ける

### コード表示

- セクションの中身（`<Section>` の開始タグと終了タグの間）を取り出してインデントをそろえる
- テンプレート内で参照している識別子のうち、インスタンススクリプトのトップレベルで定義されているもの（`import`、`let`/`const`/`var`、`function`、`class`）の定義を `<script>` ブロックとして先頭に添える。定義がさらに参照している定義も含める。元の並び順を保つ。`svelte-zukan` からの import は除く
- 元ファイルの `<script lang="ts">` の `lang` を引き継ぐ
- `<details>` で折りたたみ、既定は閉じる。コピーボタンは `<summary>` と同じ行のツールバーに置き、コードの上に重ねない（以前の、`pre` の右側に固定の余白を取る方法はやめる）
- コピーには `navigator.clipboard.writeText` を使う。失敗したら（権限がない、HTTP で開いているなど）その旨を 2 秒表示する
- シンタックスハイライトはしない

## 対応範囲

- Svelte（Vite）向けのライブラリとし、SvelteKit は対応先の 1 つとして扱う。プラグインもカタログの SPA も SvelteKit に依存しないため。素の Vite + Svelte（`@sveltejs/vite-plugin-svelte` の `svelte()`）でも SvelteKit でも同じ `zukan()` で動く
- README の説明、`package.json` の `description`（例: `Colocated component catalog for Svelte, served by a Vite plugin`）、`keywords`（`svelte`、`vite-plugin`、`component-catalog`、`styleguide`。`sveltekit` は対応先として残す）を、この位置付けに合わせる
- 必要なのは Vite 8 以上（`buildApp` フックと Environment API）、Svelte 5、Node 22.17 以上
- Kit 向けの処理（下の define）は、Kit を検出したときだけ入れる。検出は `config` フックで利用側の `plugins` を await して平らにし、名前が `vite-plugin-sveltekit` で始まるプラグインがあるかで判断する（スパイクで確認済み）。`@sveltejs/kit` がインストールされているかでは判断しない（モノレポでは、Kit を使わないアプリからも見えることがあるため）
- 素の Vite + Svelte と SvelteKit の両方を fixture で確かめる（plan の Task 7）。素の Vite では、dev の `/__zukan/`、HMR、`build: true`、`$app/*` を使わないコンポーネントの描画を確かめる

## SvelteKit の実行時 API

- 差し替えはしない。スパイクのとおり、dev ではアプリとカタログが 1 つのモジュールグラフを共有するので、カタログ側だけ解決先を変えることができない。ビルドだけ差し替えると dev とビルドで挙動が変わるので、どちらも差し替えない
- カタログの中では、Kit の実行時コードが既定の状態で動く
  - `$app/state` の `page`: `url.pathname` は空文字、`params` は `{}`、`data` は `{}`
  - `$app/env` の `browser`: `true`
  - `$app/navigation` の `goto` など: reject するだけで画面は移動しない
- これに依存する表示（現在のページによって変わるナビゲーションなど）は、カタログでは既定値で表示される。README に書く
- Kit を検出したときだけ、ビルドの環境に `define: { __SVELTEKIT_PAYLOAD__: 'undefined', __SVELTEKIT_HAS_SERVER_LOAD__: 'false', __SVELTEKIT_HAS_UNIVERSAL_LOAD__: 'false' }` を入れる
- この define は SvelteKit の内部実装（client 環境にだけ定義している置き換え）に頼っている。Kit の更新で別の置き換えが増えたり名前が変わったりしたときに気づけるよう、SvelteKit の fixture をビルドし、カタログの出力に `__SVELTEKIT_` で始まって `__` で終わる識別子が残っていないことを確かめる自動テストを置く。renovate が Kit のマイナー更新を自動マージするので、CI で回る形にする（plan の Task 7）
- `$app/paths` の `resolve` / `asset` がカタログ内でどう動くかは、plan の確認手順で確かめ、README に書く

## UI の言語

- 既定は英語。`locale: 'ja'` で日本語
- 辞書はライブラリ内に 2 言語分を持つ。i18n ライブラリは入れない
- 生成する HTML の `<html lang>` を `locale` に合わせる
- 対象の文言（現状の日本語の実装から洗い出したもの。新しい画面の文言も同じ辞書に入れる）。`groups` のキーやカタログファイルの `title` など、利用側が書いた文字列は翻訳しない

| キー           | en                                | ja                                            |
| -------------- | --------------------------------- | --------------------------------------------- |
| `nav`          | Components                        | コンポーネント                                |
| `listHeading`  | Components                        | コンポーネント一覧                            |
| `empty`        | No catalog files found. Searched: | カタログファイルが見つかりません。探した場所: |
| `notFound`     | Not found                         | 見つかりません                                |
| `loadFailed`   | Failed to load:                   | 読み込めませんでした:                         |
| `code`         | Code                              | コード                                        |
| `copy`         | Copy                              | コピー                                        |
| `copied`       | Copied                            | コピーしました                                |
| `copyFailed`   | Copy failed                       | コピーできませんでした                        |
| `previewWidth` | Preview width                     | プレビューの幅                                |
| `fullWidth`    | 100%                              | 100%                                          |

- 以前あった「Vite プラグイン `zukan()` が登録されていません」は削除する。カタログはプラグインが出すので、未登録の状態で表示されることがない
- プラグインのエラーメッセージ（ビルド時やコンソールに出る、ファイル名と行番号付きのもの）は英語に統一し、`locale` に従わない。理由: OSS として issue やログで共有されるメッセージを 1 言語にそろえる。Vite と Svelte のエラーも英語で並んで出る。プラグインの設定値の検証は UI より先に走るので、`locale` 自体が不正な場合にも出せる

## 監視

- Vite の root 外にある探索ディレクトリは、`configureServer` で `server.watcher.add` する
- `hotUpdate` で次を扱う
  - 探索ディレクトリ内の `*.<suffix>.svelte` の作成・削除: 各環境で一覧の仮想モジュールを無効化する
  - `*.<suffix>.svelte` の変更、`*.<suffix>.md` の作成・変更・削除: 対応する `.svelte` のモジュールを無効化する
  - client 環境では、`full-reload` ではなく独自イベント `zukan:reload` を送る。カタログの SPA が `import.meta.hot.on('zukan:reload')` で受けて自分だけ再読み込みする。`full-reload` は同じ dev サーバーにつながっているアプリのタブまで再読み込みしてしまうため
- 部分的な HMR にしない理由は従来どおり（`__zukan` はコンポーネントの外の export なので、Svelte の HMR では差し替わらない）。コンポーネント本体の変更は通常の HMR になり、アプリとカタログの両方に反映される

## `server.fs.allow`

- Vite の root の外にある探索ディレクトリが、既定の許可範囲（`searchForWorkspaceRoot(root)`）の外にあるときだけ、`config` フックで `server.fs.allow` に足す
- 足すときは `searchForWorkspaceRoot(root)` も一緒に入れる（`allow` を明示すると既定値が使われなくなるため）。利用側が `allow` を書いている場合は、その値に追記する

## Vite プラグイン `zukan()`

[Vite の Plugin API](https://vite.dev/guide/api-plugin) に沿って作る。

- 名前: `name: 'vite-plugin-svelte-zukan'`
- `enforce: 'pre'`。vite-plugin-svelte のコンパイルより前に変換する。README で `zukan()` を `sveltekit()` より前に置くよう案内する
- dev: `configureServer` で `server.middlewares.use` を直接呼び、`/__zukan/` で始まるリクエストに HTML を返す。HTML は `server.transformIndexHtml` を通し、仮想エントリ `\0virtual:svelte-zukan/entry` を読み込ませる。Vite の `base` を設定したアプリでも動くことを plan で確かめる
- 仮想エントリが import するもの
  - ライブラリの SPA 本体（プラグインのファイル位置からの相対で求めた絶対パス。dist では `dist/app/App.svelte`、このリポジトリでは `src/lib/app/App.svelte`）。bare specifier を使わないので、このリポジトリで自己参照の alias が要らない
  - 一覧の仮想モジュール `\0virtual:svelte-zukan/catalog`
  - ロゴ（`?url`）、`wrapper` のパス、`locale`、`title`
- 一覧の仮想モジュール:

```ts
export const catalog = [
  { group: 'ui', name: 'Button', dir: 'forms', path: 'ui/forms/Button', load: () => import('/abs/path/to/forms/Button.zukan.svelte') },
  ...
];
```

- `load` の import 先は `normalizePath` 済みの絶対パス
- ビルド（`build` が有効なとき）
  - `config` フックで `environments.zukan` を足す（`consumer: 'client'`、Kit を検出したときだけ上の define、入力は仮想エントリの JS、出力ファイル名は `assets/[name]-[hash].js` など固定の規則）
  - `buildApp` フックで `builder.build(builder.environments.zukan)` を呼ぶ。出力から entry チャンクを探し、`<outDir>/index.html` を相対パス（`./assets/...`）で書き出す
  - Kit が出す `_app/version.json` は消す
  - SvelteKit を使っていないアプリでも同じ仕組みで動く（`buildApp` は Vite 本体のフック）
- `transform` はフックフィルターを使う。正規表現は `zukan()` の呼び出しごとに、エスケープした接尾辞から作る。`?` 付きの id も対象にし、vite-plugin-svelte が CSS 用に作る仮想モジュール（`?svelte&type=style&lang.css`）と `\0` 付きの仮想モジュールは除く。handler の中でも同じ判定をする（フィルター非対応の古い Vite / Rollup 向け）
- 解析は `svelte/compiler` の `parse(source, { modern: true })` で行い、`export const __zukan = { sections, doc }` を足す
  - `<script module>` があるときは、その中身の先頭に改行を入れずに 1 行で足す
  - ないときは、ファイルの末尾に `<script module>` ごと足す
  - 挿入は `magic-string` で行い、map を返す
- `.md` は `marked` で HTML にし、`this.addWatchFile` で依存として登録する
- 変換は環境ごとに呼ばれる。結果はソースと `.md` だけで決まり、環境で分岐しない
- 解析部分、探索・一覧の組み立て、ハッシュの読み書きは、単体テストできる関数に分ける
- Vite 専用のフック（`configureServer`、`hotUpdate`、`buildApp`）を使うので、Rolldown 単体のプラグインにはしない

## 見た目

- すべて scoped CSS。利用側の Tailwind などには依存しない。カタログの UI はアプリのグローバル CSS を読み込まない（`wrapper` はプレビューの iframe の中だけ）
- 以前の公開カスタムプロパティ（`--zukan-color-bg` など 9 個）は、利用側が上書きする手段がなくなる。カタログの UI は独立した HTML で、アプリの CSS も `wrapper` も読み込まないため。既定値は内部の変数として残し、公開の仕組みとしては扱わない（README の表も削除）。テーマを変えたい要望が出たら、設定項目として足す

## パッケージ

- `svelte-zukan`: `Section`（カタログファイルが使う）
- `svelte-zukan/vite`: `zukan`
- `Zukan` コンポーネントと `entries` の export は廃止
- `svelte` の export 条件を持つので、vite-plugin-svelte が optimizeDeps から外す。`Section` とカタログの SPA が同じ `context` モジュールを共有することを、fixture で確かめる
- `dependencies` に `marked` と `magic-string`。`peerDependencies` は `svelte` と `vite`（どちらも必須。optional にしない。このパッケージの中身は Vite プラグインと、Vite が配信する Svelte の SPA なので、Vite のないプロジェクトでは使い道がない）。`@sveltejs/kit` は不要になる（`$app/*` を使わなくなる）
- `keywords` に `vite-plugin`
- `peerDependencies` の範囲は `svelte: ^5.0.0`、`vite: ^8.0.0`
- 開発用に `vite-plugin-inspect` と `@vitejs/devtools` を devDependencies だけに入れる
- `files` で `dist/**/*.zukan.svelte` と `dist/**/*.zukan.md` を除く

## ドッグフーディング

- このリポジトリでは `zukan({ groups: { ui: 'src/lib', examples: 'src/examples' }, build: true, locale: 'ja' })` と書き、上書きオプションを使う
- `src/routes` は、このライブラリの紹介ページ（`/__zukan/` へのリンク）だけにする

## やらないこと

- デコレーター、単体の CLI、シンタックスハイライト、検索、ダークモードの既定値
- SvelteKit の実行時 API（`$app/*`）の差し替え・モック
- サイドバーの階層表示（ツリー）。同名の見分けは `dir` の表示で足り、並び順でディレクトリごとにまとまるため。100 件を超えて見通しが悪いと分かったら、ID を変えずに表示だけ足せる
- `import { Section as S }` のような別名
- トップレベルの `{#snippet}` をセクションから参照したときの定義の添付
- カタログの UI のテーマを設定で変えること（今回は既定値のみ）
- ロゴのリンク先の変更、3 つ目以降の UI 言語
- ワークスペースの推移的な依存の探索
- `groups` のキーを数字だけにしたときの並び順の保証。JavaScript のオブジェクトは、整数に見えるキー（`'1'`、`'2'`）を宣言順ではなく数値順で先に並べる。グループ名として数字だけを使う場面は少なく、配列の形のオプションを足すほどではないため。README に一行書く
- カタログの UI の狭い画面向けのレイアウト。カタログは開発者がデスクトップのブラウザで使うもので、スマートフォンの幅はプレビューの幅プリセットで確かめられるため
- プレビューの iframe だけが再読み込みされたときの高さの追従。カタログファイルや `.md` の変更はカタログ全体の再読み込み（`zukan:reload`）になり、コンポーネントの変更は iframe の中の HMR で済むので、iframe だけが読み込み直される場面がない
